# تمكين الاختبارات للضيوف بدون تسجيل دخول

تعديل صفحة الاختبار وسياسات قاعدة البيانات للسماح للطلاب بحل الاختبارات كضيوف (anon) دون الحاجة لتسجيل الدخول. تم تغيير `checkAuth` من protected إلى unprotected، وإضافة modal لجمع اسم الضيف اختيارياً، وتعديل دالة submitExam لحفظ النتائج مع `user_id: null`، بالإضافة إلى إضافة سياسات RLS في Supabase للسماح بإدراج محاولات الضيوف.

**Watch for:** فجوة في فحص البيانات المُدخلة من الضيف (likely)، محاولة الوصول لـ preview mode كضيف تُحظر بشكل صحيح (confirmed)، رسالة ما بعد الاختبار تشجع على التسجيل (confirmed)، لكن تجربة المستخدم للضيف بعد الاختبار فيها نافذة `confirm` بدلاً من واجهة مستخدم أفضل (confirmed).

**Verdict**: CHANGES_REQUESTED

## High-level view

تحولت الصفحة من protected إلى unprotected بنجاح عبر تغيير `checkAuth({ protected: false })`، وأصبح الكشف عن الضيف يتم بفحص `!user` بعد checkAuth مباشرة. إذا كان الزائر ضيفاً ووضع التشغيل هو "run"، يظهر modal لجمع الاسم اختيارياً ثم يُنشأ كائن `guestUser` بـ `uid: null` و `isGuest: true` لتمريره لـ loadExam.

في submitExam، user_id يُرسل كـ null عندما يكون `user.isGuest` true، وهذا يوافق سياسة RLS الجديدة التي تسمح بإدراج attempts من anon بشرط `user_id IS NULL`. هذا يمنع الانتحال لأن الضيف لا يستطيع أن يُحدد user_id لمستخدم آخر.

سياسة SQL تتضمن `DROP NOT NULL` على user_id وإضافة سياسة INSERT للـ anon مع `WITH CHECK (user_id IS NULL)`، وسياسة SELECT للمدرسين والإداريين لعرض محاولات الضيوف. التصميم الأمني صحيح لأن WITH CHECK تفرض القيد من جانب قاعدة البيانات.

بعد إنهاء الاختبار، الضيف يحصل على نافذة confirm تحتوي النتيجة ودعوة لإنشاء حساب، بينما المستخدمون المسجلون يُحوَّلون إلى صفحة النتائج. فرق UX واضح بين الاثنين.

Modal الضيف في HTML يحتوي حقل نص اختياري وزرّي "ابدأ الاختبار" و "تسجيل الدخول". التنسيق inline CSS بدلاً من استخدام ملف CSS خارجي، وهذا مقبول لعنصر صغير لكن غير متسق مع بقية المشروع.

## تحويل الصفحة من protected إلى unprotected

تغيّر `checkAuth({ protected: true })` إلى `checkAuth({ protected: false })` في DOMContentLoaded. يتم الكشف عن الضيف عبر `const isGuest = !user` مباشرة بعد checkAuth، ثم يُستخدم isGuest لتوجيه التدفق.

وضع المعاينة يُرفض للضيوف برسالة خطأ واضحة: "وضع المعاينة متاح للمعلمين فقط".

في وضع التشغيل "run" للضيف، تُستدعى دالة `showGuestNameModal()` لجمع الاسم اختيارياً، ثم يُنشأ كائن guestUser به:

```javascript
const guestUser = {
  uid: null,
  email: null,
  name: guestName || "ضيف",
  full_name: guestName || "ضيف",
  isGuest: true,
  isTeacher: false
};
```

## Modal جمع اسم الضيف

أُضيف عنصر div بمعرّف `guestModal` في HTML بتنسيق inline. دالة `showGuestNameModal()` تُرجع Promise تُحل عندما ينقر المستخدم على "ابدأ الاختبار" أو يضغط Enter.

**Concern:** لا يوجد تنظيف للإدخال. إذا كتب الضيف `<script>alert('XSS')</script>` كاسم، سيُحفظ في قاعدة البيانات كما هو. عند عرضه في صفحات النتائج، قد يتم تنفيذ الكود إذا لم يكن العرض آمناً. حتى لو كان العرض يستخدم textContent (آمن)، من الأفضل تنظيف الإدخال عند الحفظ لمنع تلويث البيانات.

**Concern:** التنسيق كله inline CSS داخل HTML. هذا لا يتناسب مع بقية المشروع الذي يستخدم ملف CSS خارجي. يجب نقل التنسيق إلى ملف CSS لتنسيق موحد وإمكانية تطبيق الثيم (dark mode/light mode) بشكل صحيح.

## تعديل submitExam لإدراج محاولة الضيف

في دالة submitExam، تغيّر payload ليستخدم:

```javascript
user_id: user.isGuest ? null : (user.uid || user.id),
student_name: user.full_name || user.name || user.email || "ضيف"
```

عندما يكون `user.isGuest` true، user_id يُرسل كـ null. هذا يتوافق مع سياسة RLS الجديدة التي تتطلب `user_id IS NULL` للضيوف.

بعد نجاح الإدراج:
- **للضيوف:** يعرض `confirm` بعد 1.5 ثانية يحتوي النتيجة ويسأل "هل تريد إنشاء حساب الآن؟". إذا وافق، يُحوّل لصفحة التسجيل.
- **للمستخدمين المسجلين:** يُحوّل لصفحة النتائج بعد ثانيتين.

**Concern:** استخدام `confirm` للضيوف متطفل وليس تجربة مستخدم مثالية. نافذة confirm تظهر فوق المحتوى وتوقف التفاعل. سيكون أفضل استخدام modal مخصص أو toast notification مع زر "إنشاء حساب" وزر "إغلاق" بدلاً من confirm.

## سياسات RLS وأمان قاعدة البيانات

ملف `guest_exam_rls.sql` يتضمن:

1. **DROP NOT NULL على user_id:**
```sql
ALTER TABLE public.attempts ALTER COLUMN user_id DROP NOT NULL;
```

2. **سياسة INSERT للمستخدمين المجهولين (anon):**
```sql
CREATE POLICY "Anon Insert Guest Attempts" ON public.attempts
  FOR INSERT
  TO anon
  WITH CHECK (user_id IS NULL);
```

هذه السياسة تسمح للـ anon (الضيوف غير المصادقين) بإدراج صفوف في attempts **فقط** إذا كان user_id = NULL. `WITH CHECK` هو قيد على جانب قاعدة البيانات لا يمكن تجاوزه من الكود. هذا يمنع الانتحال: لو حاول كود ضار إدراج محاولة بـ `user_id = 123` (محاولة الانتحال لمستخدم آخر)، ستفشل RLS ولن تُدرج الصف.

3. **سياسة SELECT لعرض محاولات الضيوف:**
```sql
CREATE POLICY "Admin Read Guest Attempts" ON public.attempts
  FOR SELECT
  TO authenticated
  USING (
    user_id IS NULL
    AND (
      (auth.jwt() -> 'user_metadata' ->> 'role') = 'admin'
      OR (auth.jwt() -> 'user_metadata' ->> 'role') = 'teacher'
    )
  );
```

هذه تسمح للمدرسين والإداريين (فقط) بقراءة محاولات الضيوف.

**Concern:** لا يوجد rate limiting أو قيد على عدد المحاولات من نفس الضيف. ضيف واحد يمكنه إرسال آلاف المحاولات. إذا كانت هذه مشكلة (spam أو إساءة استخدام)، ستحتاج إضافة rate limiting على مستوى التطبيق أو سياسة أكثر تعقيداً تفحص IP أو timestamp.
